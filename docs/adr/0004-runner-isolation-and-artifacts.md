# ADR 0004: Runner Isolation and Artifacts

- Status: Accepted
- Date: 2026-07-25
- Issue: #2

## Context

Runner workloads process repository content and may execute untrusted commands.
Running them inside the web or worker process would expose control-plane
credentials, database access, source checkouts, and the host filesystem.
Artifacts can also contain sensitive client data and must not become an
uncontrolled file-sharing channel.

## Decision

The worker orchestrates runs but delegates command execution to an isolated,
ephemeral runner boundary. A runner implementation must provide:

- a fresh sandbox per run;
- no control-plane database route or credentials;
- deny-by-default outbound network access, enabled only by an explicit,
  auditable policy for a destination set;
- a read-only source snapshot and a dedicated writable scratch directory;
- a non-root identity, dropped capabilities, and no privileged host sockets;
- CPU, memory, process-count, disk, and wall-clock limits;
- explicit cancellation and termination with no sandbox reuse.

The default local Compose stack keeps `RUNNER_ENABLED=false` and does not mount
the Docker socket. A later local runner adapter must preserve the same contract;
enabling it is not implied by starting the web and worker services.

The worker sends a minimal execution envelope containing opaque run and input
references, command policy, limits, and artifact upload capability. It does not
send integration credentials or general control-plane tokens. The runner emits
structured status and uploads outputs through a narrow artifact interface.

Artifacts are immutable after finalization. Stored metadata includes tenant and
run ownership, media type, byte size, checksum, creation time, retention class,
and scan status. Storage keys are generated by the system and never derived
directly from user paths. Reads require authorization against metadata; storage
location alone grants no access.

Local development uses the `artifacts` Compose volume. Non-local environments
must use storage with encryption, lifecycle controls, and short-lived signed
access. Executable or active content is quarantined until policy checks pass.

## Consequences

- Compromising a runner does not inherently grant database or worker access.
- Network-requiring jobs need a reviewed policy instead of ambient egress.
- Runner startup has overhead, accepted in exchange for a smaller blast radius.
- Artifact cleanup is asynchronous and driven by retention state in PostgreSQL.
- The control plane can change runner implementations without changing domain
  run semantics.
