# f(AI) Control — архитектура

Владелец → штатный GUI + одно расширение fai-control → Paperclip Core.
Core владеет tasks, runs, review/approval, membership, costs, PostgreSQL и
файловым хранилищем. Всё размещено на нашем VPS. Учётные записи относятся
к нашей инсталляции; Paperclip Cloud для работы не требуется.

Расширение: wizard, документы/контекст, lifecycle постоянного Hermes,
настройка чатов и внешних подключений. Используются SDK/API, plugin state и
UI slots. Нет прямых записей в Core tables, второго controller/scheduler,
подмены router или DOM/CSS-ребрендинга Core.

## Исполнение
На проект один Hermes с отдельными workspace/memory/sessions/контекстом.
Hermes владеет PM, вызовами Developer CLI, одобренными DevOps и чатами.
QA — отдельный для каждого проекта `codex_local`, другая native identity,
отдельные задача/сессия/рабочая область, без переписки соседних проектов.
Hermes и QA используют один Codex-login этого проекта из его изолированного
`CODEX_HOME`; другой проект проходит отдельную device-auth и не наследует login.
QA запускается native review stage, не таймером. Запись агента сама по себе
не тратит токены; расход возникает при вызове модели. Model/effort, критерии
и ограничение повторных циклов должны быть реальной конфигурацией, не прозой.

Core передаёт завершённую Dev-задачу reviewer, затем владельцу; запрос изменений
возвращает исходному исполнителю. QA даёт commit, критерии, дефекты, проверки.
QA сам исправляет только детерминированные lint/format дефекты без изменения
поведения, публичного текста или ожиданий тестов; функциональные дефекты возвращает
Developer одним сводным отчётом. При native `maxReviewRounds=2` после одного
автоматического цикла второе отклонение эскалируется ответственному человеку;
плагин не меняет review policy задачи автоматически.
Самопроверка той же identity не считается независимой QA.
Приёмка разработки не разрешает production автоматически. Merge/deploy
имеют явный объект разрешения: PR/commit и конфигурация выпуска. Hermes
выполняет DevOps после решения владельца, сохраняет результат в native задаче.

## Трекер
Native tasks — целевая единственная рабочая доска. GitHub — код/PR/история.
После ручного создания проекта переносится один раз активная работа, сохраняются
ссылки на источники, старые GitHub-статусы перестают редактироваться.
Внешний Project-коннектор не нужен для этого пилота. Провайдерские границы
repository/tracker/messenger/native agent adapters остаются независимыми.

## Credentials и восстановление
GitHub настраивается централизованно у Core штатным gh/git helper.
Новый разрешённый проект не требует повторного ввода аккаунта; проектный
credential имеет приоритет. SSH/DevOps клиента не наследуются автоматически.
Общего Codex-login компании нет. Один проектный login обслуживает Developer и
QA этого проекта, но не переносится в соседний проект. Это не объединяет их
native identity, задачи, рабочие области и инструкции.
Gateway имеет индивидуальный ключ и native adapter. Перезапуск сохраняет
или штатно восстанавливает адрес привязки, identity и контекст. Готовность
требует аутентифицированного readback, а не одного наличия файлов.

## Чаты
Internal Telegram и optional client Element/Telegram обслуживает Hermes.
Для разработки клиентский канал выключен. Клиентский профиль изолирован.
Статусы native событий отправляются через штатный hermes send в разрешённую
группу, без вызова LLM, второго транспорта или копии истории.
Подтверждение конфигурации отдельно от live delivery и защиты от дублей.
GUI и Telegram должны ссылаться на одну native задачу.

## Границы приёмки
Компоненты и unit-тесты не доказывают полный перенос. Текущие пробелы и
доказательства находятся в Project, не копируются в этот документ.
Полный цикл проверяется после ручного создания проекта на одной простой задаче.
Внешний Project/клиентский Element принимаются отдельными срезами по потребности.
Канонический ADR: docs/adr/0007-paperclip-core-and-extension.md.
Документы не содержат секретов и не дают разрешений на production.
